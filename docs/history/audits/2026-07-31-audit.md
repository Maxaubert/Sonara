# Sonara Audit - Final Report

38 verified findings, merged to 33 entries. Verified myself before ranking: `summarizer.py:165`, both `launch_spec` bodies, `_EARCON_SPECS` vs. every `_earcon()` call site, and the Windows hooks template event set.

## CRITICAL / HIGH - fix now

### H1. `critical` Daemon spawns with no `cwd`, so the summarizer resolves `claude` out of the user's project directory
`src/sonara/summarizer.py:165`, `src/sonara/platform/windows/supervisor.py:755`, `src/sonara/platform/windows/supervisor_loop.py:72`, `src/sonara/daemon.py:2729`
(merges [33] + [34]: one defect, two consequences)

```python
# summarizer.py:165 - runs in the DAEMON, so cwd=~ on line 176 does not apply here
exe = shutil.which(argv[0]) or argv[0]
```
```python
# supervisor.py:755 and supervisor_loop.py:72 - no cwd= in either spawn
kwargs = dict(creationflags=_SPAWN_FLAGS, stdin=..., stdout=..., stderr=err, env=env)
```
```python
# daemon.py:2729
argv, kwargs = get_platform().supervisor.launch_spec()
subprocess.Popen(argv, **kwargs)
```
Neither spawn path sets `cwd`, so the daemon inherits the caller's working directory. Lazy start comes from a Claude Code hook, so that is the project folder, and the daemon holds it for its whole lifetime. Two consequences:

- **Code execution.** On Windows CPython `shutil.which` prepends the current directory and applies PATHEXT. With `summary_mode` on, every finished turn resolves `claude` against the untrusted repo root. A `claude.exe` there is executed as the user, on every turn, silently. (`.bat`/`.cmd` payloads do *not* fire: cmd.exe re-resolves them against the child's `cwd=~`. A real PE image does.) Mitigating factors: `summary_mode` defaults to False (`config.py:20`), and Claude Code sometimes injects `NoDefaultCurrentDirectoryInExePath` into hook children, but the live daemon on this machine does not have it.
- **Directory lock.** Windows pins an open handle on a process's cwd, so the user cannot delete or rename that project folder while Sonara lives. `cli.py:459-462` already documents this exact failure mode from the scheduled task.

Fix: `cwd=str(paths.SONARA_DIR)` in both `launch_spec`s (one line each) plus `shutil.which(argv[0], path=os.environ.get("PATH"))` and no bare-name fallback.

### H2. Four earcon kinds the daemon plays have no bundled wav - nav, session-change and summary-failure chimes are permanent no-ops
`src/sonara/platform/windows/earcons/generate.py:108`, `src/sonara/daemon.py:801/807/810/886/958/1786/2472/2507`
(merges [0] + [25])

`_EARCON_SPECS` defines exactly six names: `permission, choice, plan, error, turn_done, ready`. `daemon.main()` builds the speaker table from `default_earcons()`, and `config.DEFAULTS` has no `earcons` key, so those six are all that ever exist. Eight of the nine `_earcon()` call sites in daemon.py ask for names that are not in the table:

```
801: self._earcon("nav" if moved else "nav_edge")
886: self._earcon("session_change")
958: self._earcon("nav" if self._flush_all() else "nav_edge")
1786: self._earcon("summary_failed")
2472/2507: self._earcon("session_change")
```
`Speaker.earcon()` returns silently on a missing key. Conversely `plan.wav` and `ready.wav` ship with no caller (`hooks_entry.py:58/92` removed them). The most damaging losses: `summary_failed` is the *only* feedback for an empty digest, and nav-edge / flush-to-end have no other feedback channel at all. Tests assert the wrong side of the contract (`test_win_earcon.py:51 assert len(...) == 6`) and daemon tests record kind strings against a fake speaker, so the whole suite is green.

### H3. `paths.repo_root()` is `__file__`-derived, so `sonara install` from the installed launcher bricks the daemon
`src/sonara/cli.py:639` (with `cli.py:646/652/675`)

`repo_root()` means "two dirs up from this file", true only under `<repo>/src/sonara`. `_copy_app()` copies only `src/sonara` into `~/.sonara/app`, and `~/.local/bin/sonara.cmd` runs with `PYTHONPATH=~/.sonara/app`, where `repo_root()` returns `~/.sonara` - a directory with no `src/` and no `bin/`. Running `sonara install` through that launcher: step 1c writes the STOPPED sentinel via `stop_sonara(sup)`, step 2's `copytree("~/.sonara/src/sonara", ...)` raises FileNotFoundError, the handler prints "Could not copy the runtime" and returns 1 **before** step 5b clears the sentinel. Sonara is now permanently off: hooks will not respawn it (`ensure_running` returns early on the sentinel) and the printed error does not mention the cure (`sonara start`). The plugin path `/sonara:install` is unaffected - `bin/sonara-bootstrap.ps1:91-92` sets PYTHONPATH to the checkout.

### H4. Windows hooks template is missing PostToolUse, so `CHOICE_ANSWERED` never fires for settings.json installs
`src/sonara/platform/windows/supervisor.py:263-405`

Verified: `hooks/hooks.json` declares 8 events (`MessageDisplay, Notification, PostToolUse, PreToolUse, SessionEnd, SessionStart, Stop, UserPromptSubmit`); the hand-copied `HOOKS_JSON_TEMPLATE` declares 7 - PostToolUse is absent. That hook is the only producer of `MsgType.CHOICE_ANSWERED` (`hooks_entry.py:72-77`), so `daemon.py:961-967 self._user_caught_up(session)` (the #83 stale-backlog flush) is unreachable for every user who installed without enabling the plugin - the documented path (`supervisor.py:838`). Symptom: after answering a blocking question, the stale pre-question backlog keeps speaking. No test compares the two sets.

## LOW - dead code and cleanup

**Duplicated / drifted defaults and logic**
- [2]+[28] `summary_settle_ms` is in `_PAGE_KEYS` and the settings page but not in `config.DEFAULTS` (`config.py:24`). `/api/state` returns `null`; the number input goes blank and the readout says "null ms". The daemon's effective 600 ms (`daemon.py:1563` fallback) is correct.
- [31] `daemon._duck_level()` falls back to 20 while `DEFAULTS` says 30 (`daemon.py:2217`). Unreachable in production (load_config always materializes the key) except via the `except` branch on a corrupt value.
- [11] Voice-to-engine routing implemented three times (`tts.py:640`, `_prefetch_decision_audio`, `_cue_voice`); all three currently agree, and the authoritative copy sits in the Windows backend for two platform-independent engines.
- [12] `daemon_pythonw()` vs `cli._daemon_python()`, and `_probe_python_version` module copy vs method copy (`supervisor.py:168`). Only the monkeypatchable method copy is tested; the module copy is what spawn uses.

**Concurrency and lifecycle**
- [16] `Speaker.speak` cancel/abandon handoff: the helper reads `abandoned` into a local under the lock, then releases before `done.set()`; a cancel landing in that window means neither side terminates the proc (`speaker.py:95`). Two-bytecode window; trivial fix.
- [17] `_pending_preamble` check-then-act outside the lock (`daemon.py:2492/2533`); realistic outcome is a stale/lost preamble, not the TypeError.
- [18] `_teardown_session` **pops** `_settle_gen` right after `_cancel_settle` bumps it (`daemon.py:350`), resetting the monotonic guard so a blocked timer callback can pass it after a re-arm. Should bump, not pop, matching `_summary_gen`.
- [24] `_settle_fire` is the only daemon dispatch path with no catch-all (`daemon.py:1574`); a thread-start failure kills the Timer thread after `_settle_pending.discard`, so the turn is lost with no cue and an allocated seq can wedge the reorder buffer.
- [15] `_warm_chatterbox_async` coalescing never engages: `_run`'s `finally` clears `_warm_inflight` while the inner `_warm` thread is still running (`daemon.py:1206/1237`). Unbounded thread spawn; queued warms serialize on one client lock, so real latency impact is small.
- [30] `pausing.resume_from_state_file()` has the same finally-clears-on-failure defect as M10 (`pausing.py:175`). No compounding; cost is one manual Play press.

**State and hygiene**
- [9] `_replay()` writes `ch.items` directly and never sets `has_decision` (`daemon.py:1334`), so a replayed blocking question loses router preemption and waits for the fallthrough. (`_enqueue` is never called with `is_decision=True`, and `_user_caught_up` does maintain the flag - the break is confined to `_replay`.)
- [36] Duck restore matches by raw PID (`ducking.py:171`); a recycled PID gets an unrelated volume written. The by-name branch is deliberate and correct - drop that half of the concern.
- [32] `speechd.log` never rotates; both `launch_spec` copies `open(LOG_PATH, "a")` per restart (the natural rotation point) and leak the handle. Same for `hotkeyd.log`.
- [38] Task Scheduler XML built by string interpolation with no escaping of username or paths (`supervisor.py:99`); only `&` is realistically reachable (an "R&D" account), and it fails loudly-ish at install ("warning: schtasks ... returned N").

**Dead code**
- [3] `_drop_pending`, `_resume`, `_audio_pause_on` in daemon.py have zero callers anywhere in src, tests, bin, hooks or tools. `_resume`'s docstring documents pause semantics the live handler no longer follows.
- [4] macOS hotkeyd debris: `keymap.write_resolved()` / `HOTKEYD_RESOLVED_PATH` written on every install and never read; `HOTKEYD_BIN_PATH` has no consumer at all. The stale `hotkeyd.resolved.json` actively misleads anyone diagnosing hotkeys.
- [5] `import os` unused in `kokoro.py:18`.

## CROSS-CUTTING THEMES

**1. There is no failure channel, and the tool is eyes-free.**
This is the systemic defect. Every layer degrades to silence: `Speaker.earcon()` returns on a missing key (H2), `_start_hotkeys` swallows a keymap error with a bare `pass` (M4), Chatterbox returns rc=0 after dropping every chunk (M5), `_prefetch_decision_audio` is wrapped in `except Exception: pass`, ducking's sweep is wrapped in `except: pass` (M10), the singleton mutex path returns with no log line (M11), `_settle_fire` has no guard (L). A sighted user of a normal CLI would see a traceback; here every one of these produces *exactly the same observable state as working correctly but having nothing to say*. Recommendation: one `_signal_failure(reason)` that always logs to speechd.log and always plays the `error` earcon (mute-exempt), and make every `except: pass` in the speech path call it.

**2. Every policy that crosses the core/platform seam exists in two hand-maintained copies, and they have already drifted.**
Confirmed pairs: hooks event set (H4, drifted - PostToolUse missing), `launch_spec` (M12, drifted - different PYTHONPATH root), interpreter resolution (L, not yet drifted), voice-to-engine routing (L, three copies, not yet drifted), `duck_level` default (L, drifted 20 vs 30), `summary_settle_ms` default (L, exists only as an inline `.get()` fallback). The comments even say "Parity with ...", which is a maintenance promise standing in for a shared function. Two of six have already broken. Fix pattern: one function, and where a second copy is unavoidable, one test asserting equality of the two.

**3. `__file__`-derived identity inside a package that is deliberately redeployed.**
`repo_root()` (H3), both `launch_spec`s (M12), `default_earcons()` path resolution (M8), and the log path all answer "where am I" from `__file__`, but the package intentionally lives in two places (`<repo>/src/sonara` and `~/.sonara/app`) with different shapes. Nothing validates the answer and nothing logs it, so "which code is actually running" is unobservable - which is exactly the runtime-deploy-drift trap already recorded in project memory.

**4. Persisted state permanently shadows code, with no version, no revalidation, and no migration.**
`save_config` writes the merged DEFAULTS (M7), so config.json outranks every future default. The earcon map bakes absolute paths once and never rechecks them (M8). Duck/pause state files are cleared in `finally` even when restore failed (M10, L). Duck restore trusts a recorded PID (L). These compose badly: **the H2 earcon fix is undeliverable to existing users until M7 and M8 are fixed.** That coupling is the single most important sequencing fact in this report.

**5. Sonara reaches outside its per-user boundary.**
Same class as the already-known `_kill_stray_daemons` PowerShell sweep: a `Global\` kernel object (M11), a machine-wide mixer rewrite with a destructible undo record (M10, L), an inherited handle on the user's project directory (H1), and executable resolution against an untrusted cwd (H1). Sonara is a per-user speech layer; it should own nothing outside `~/.sonara` and its own audio session.

**6. No wall-clock bound on external work, and the blocked thread holds the lock the speech path needs.**
`urlretrieve` with no timeout holding `KokoroEngine._lock` (M2), a summarizer worker whose `finally` is after the blocking call (M1), `ChatterboxClient._request` holding `self._lock` for a 90 s round trip (L). In each case the blocking call is not merely slow, it is *unrecoverable without a daemon restart*, because the thread that would have released the lock is the one that is stuck.

**7. The tests validate the wrong side of every contract they touch.**
`test_win_earcon.py:51` asserts `len(default_earcons()) == 6` - it locks in the bug (H2). Daemon tests inject a fake speaker that records kind strings, so a missing wav is invisible. CLI tests cover the monkeypatchable *method* copy of interpreter resolution while the *module* copy is what spawn uses (L). No test compares the two hooks templates (H4). Combined with the fake-winrt shim that returns early on win32, the suite's green state carries almost no information about Windows behavior. Recommendation: for each cross-copy pair, add the equality test - that is a handful of assertions that would have caught H2, H4 and M12.

21. **M9** one lock around `_get_synth` and the voice+rate+synthesize sequence, or a per-call synthesizer.
22. **M6** route previews through the earcon helper process.
23. **M13** `Router.rearm_announce()` / `clear_announce()`; make the three-field tuple unwritable from outside.
24. **L** `voices.engine_for()`, log rotation, XML escaping, PID+start-time identity in duck restore.

Independent throughout: H1, M14, M11, M2, M9, M6, log rotation. Sequenced: M7 -> M8 -> H2 (hard dependency), and the H3 guard before the H3 refactor. Refactors: H3 (15), H4, M12, M3, M13. Everything else is a one-liner or a handful of lines.

## WHAT THIS AUDIT DID NOT COVER

- **No execution.** Nothing was run: no test suite, no daemon, no `sonara install`, no Windows behavior observed. Every finding is a source read. Where empirical confirmation mattered it is flagged inline (M1's grandchild-pipe mechanism was not reproduced).
- **The deployed copy at `~/.sonara/app` was not audited**, per instructions - only the repo. Drift between the two is itself a finding (M12) but its current magnitude is unmeasured.
- **The test suite was not audited as code.** ~18.2k lines across 129 files were consulted only where a test proved or disproved a claim about production behavior. Coverage gaps beyond the ones named in theme 7 are unknown, and the fake-winrt shim's fidelity was not assessed.
- **Not reviewed in depth:** `webui.py` request handling (auth, binding address, CSRF, path traversal on `/api/preview-audio`), `settings.html`'s ~380 lines of client JS beyond the two values traced, `assembler.py`, `router.py` scoring logic beyond the decision-preempt loop, `chatterbox_worker.py` and the GPU worker protocol, `cli.py`'s command surface beyond `install`/`stop`, `keymap.py` beyond `resolve_keymap`, and `hooks_entry.py` beyond the event mapping.
- **No security review of the summarizer prompt path** (prompt injection from turn content into `claude -p`), of the digest cache/`digest_store`, or of file permissions on anything in `~/.sonara`.
- **No performance, memory, or latency analysis**, and no audit of the neural engine venvs' provisioning or dependency pinning.
- **Correctness of the speech content itself** (chunking, sentence splitting, SSML/text normalization) was not evaluated.
- **`_kill_stray_daemons`**, named in the brief as a known hazard, was treated as already-known and not re-reported; the search was for *other* instances of that class, which produced H1, M10 and M11.
